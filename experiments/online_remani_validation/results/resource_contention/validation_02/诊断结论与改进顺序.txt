REMANI / 后台MPPI / 接入MPPI：诊断结论
2026-10-15，Asia/Shanghai

一、主要结论

本批数据不支持“MPPI抢走CPU，导致REMANI普遍长时间等待”这一解释。
MPPI确实增加了计算负载，也存在小幅干扰；同一静态求解请求下，运行MPPI使
墙钟耗时平均增加约1.12%。这种干扰可能让恰好接近0.60秒预算的请求越界，
不能说完全没有竞争，但它解释不了主要的秒级等待和静态持续停滞。

本次确认了三个应分别处理的问题：
1. 当前REMANI在不启动MPPI时也会耗尽0.60秒优化预算。
2. 优化器可以数值收敛，但输出仍违反轮速/轮加速度约束，最终被拒绝。
3. 原控制链存在参考冻结后的横向误差恢复死锁；此时新轨迹早已交付。

“优化超时”“优化收敛但轨迹验收失败”“轨迹已交付但控制停滞”不是同一现象。

二、实验范围和可信度

正式数据仅使用 validation_02：空旷、突现静态障碍、四动态障碍三个场景，
每场景三组、各重复两次，共18次在线闭环，另做8次相同优化请求配对求解。
保存了3365次进程/线程/各核CPU采样、99个完整求解阶段记录。

A：当前工程REMANI + 原Tracker，不启动MPPI。
B：与A相同，再运行V12 MPPI内核和候选/制动复核；所有MPPI输出隔离。
C：当前V12协同模式，MPPI实际执行，REMANI提供并刷新参考。

三组使用相同的原生二进制、MPPI库、实车展开参数、固定机械臂姿态和V12检测器。
A/B参数逐项相等；后台输出隔离、唯一控制发布者、节点PID与采样覆盖均通过审计。
CPU按200ms采样；100%代表占满一个逻辑CPU，主机可用6个逻辑CPU。
REMANI进程包含地图线程，优化线程自身CPU时间另外测量。

这是本机隔离ROS数值仿真，场景由合成点云与带执行滞后的差速底盘产生。
没有运行真实硬件和完整实车SLAM负载，不是Gazebo或实车验收。
A组沿用当前工程已有的控制器和预算策略；每场景仅两次，适合定位问题，不能据此
估计统计成功率或代表原论文、实车的整体性能。
原生产源码98项哈希未变。构建和运行数据均保存在experiments目录。
开发批次validation_01的节点PID采集有误，已标为无效，不混入本次CPU统计。

三、CPU和优化超时结果

下表为每场景两次试验的进程CPU均值，100%是一个逻辑核：

场景        A：REMANI/MPPI       B：REMANI/MPPI       C：REMANI/MPPI
空旷        166.3% / 0          165.7% / 55.0%       154.9% / 63.0%
静态        168.9% / 0          168.6% / 76.0%       153.2% / 62.5%
四动态      158.8% / 0          155.2% / 44.6%       151.4% / 48.1%

优化器调用与预算超时：
A：14次优化调用，4次预算超时。
B：17次优化调用，3次预算超时。
C：17次优化调用，7次预算超时。

后续状态、搜索结果和规划入口不同，不能把C超时次数较多直接归因于CPU争抢。
累计优化阶段中，线程实际CPU时间/墙钟时间分别为：
A：99.33%；B：99.48%；C：98.55%。
运行队列等待占墙钟时间分别约0.31%、0.19%、0.50%。
这些请求的大部分时间都在实际计算，而不是排队等待CPU。
已用两个同核忙算进程验证CPU/调度等待计数：约1.5秒墙钟中各占约0.75秒计算和0.75秒等待。

0.60秒是当前改造流程的优化预算；它会在回调检查点中断求解，不能抢占正在进行的
单次代价计算，所以实测函数总耗时可能略超过0.60秒。
动态场景存在完成仅7～13次代价/梯度计算就耗尽预算的请求。
因此不能把问题只理解为“迭代次数太多”，也不能认为只缩短轨迹就一定足够。
哪些碰撞查询或梯度构造最耗时，仍需要函数级剖析；本次定位到请求/优化阶段。

监测器自身约消耗每200ms的5.7～11.0ms线程CPU，约一个逻辑核的2.9～5.5%。
该观测开销已记录，不能称为完全无扰动。三组均启用同一采集器。
MPPI完整周期仍有少量50ms超时：后台组共7次，接入组共10次；未达到硬实时保证。

四、相同请求的配对诊断

选择本轮一次静态参考刷新，保持同一个优化输入和序列化地图回调，分别暂停/运行
本次MPPI进程，并以0.60秒与1.50秒预算各做两次。8次输入指纹完全相同。

预算0.60秒：
  MPPI暂停：墙钟504.916ms，线程CPU501.513ms，调度等待0.687ms。
  MPPI运行：墙钟507.094ms，线程CPU503.030ms，调度等待2.196ms。
预算1.50秒：
  MPPI暂停：墙钟503.094ms，线程CPU500.433ms，调度等待0.896ms。
  MPPI运行：墙钟512.227ms，线程CPU505.193ms，调度等待3.314ms。

合并两种预算，暂停与运行时墙钟均值分别约504.005ms和509.661ms，差约1.12%。
每次均完成93次代价/梯度计算并数值收敛，没有预算超时。
但8次最终轨迹验收全部失败，原因完全相同：
  轨迹相对时间1.54秒处，左轮角速度3.454674rad/s。
  物理上限3.28rad/s，当前原生验收容差5%，验收阈值3.444rad/s。
  计算结果超过验收阈值，因此被拒绝。

这说明：数值收敛不等于约束可行；放宽到1.50秒不会改变已经收敛的这个不可行解。
当前流程用软惩罚优化轮速/轮加速度，再做最终硬检查，存在有效轨迹交付不稳定问题。
这次配对是新采集的静态请求，不是对历史那一次超时请求的精确重放；不能据此宣称
每次动态超时都与MPPI完全无关，也不能排除缓存/带宽等非调度干扰。

五、静态停住的另一条已证实原因：控制恢复死锁

A/B共4次静态任务均超时未到达，但末尾都已经发布了新参考，trajectory_count=2。
safety_limit=-1，说明没有激活零限速；virtual_time停住，time_scale=0。
根据保存的多项式系数和最终虚拟时间精确重算，而非GIF目测：
  A第1次：横向误差12.182cm；A第2次：13.009cm。
  B第1次：横向误差12.606cm；B第2次：12.451cm。
四次前后方向误差均约1e-15m，朝向误差约1e-14rad。

当前MMctrl在位置误差达到16cm时冻结参考，要求误差回到5cm内才恢复。
冻结后参考线速度和角速度归零。Tracker控制律为：
  v = v_ref*cos(e_yaw) + k_x*e_x
  w = w_ref + k_yaw*e_yaw + k_y*v_ref*e_y
当v_ref=w_ref=0，且e_x、e_yaw已经消除时，v和w都变成零。
剩余约12～13cm的纯横向误差无法自行消除，MMctrl恢复条件一直不满足。

所以这四次静态“任务超时”后半段主要是执行恢复死锁，不能解释为规划器一直在计算。
C由MPPI拥有实际执行权限，原MMctrl冻结不直接控制底盘，本轮6次任务均到达。
这支持已有执行权限分离的作用，但不能把全部差异当成MPPI避障代价更优的证明。
A/B四动态各2次均发生投影碰撞，C四动态2次到达；失败记录完整保留。

六、REMANI与MPPI尚未协同好的具体位置

1. 有状态反馈，但没有完整的优化初值反馈。
   当前MPPI的局部展开回调只保存路径。慢层主要检查旧参考是否被挡，然后从当前反馈
   状态调用自己的搜索/优化，没有把已经通过检查的局部绕行直接转换成可行初始化。
   快层已经找到绕行方案，并不自动意味着慢层下一次优化更容易成功。

2. 异步求解期间机器人仍在移动，新参考需要显式接续。
   本轮C重规划期间最大实际位移约16.5cm；成功请求结束时，规划输入起点与当时实际
   位置的差也达到约16.5cm。求解开始时取实际位置，仍不足以保证交付时状态和时序一致。

3. 约束处理方式并不一致。
   MPPI对候选控制逐步执行轮速/加速度限幅和完整展开复核；原生优化通过软惩罚处理
   可行性，再允许一定验收容差。几何投影统一不能自动统一这种动态可行性和时序语义。
   本次测试的是冻结的原V12，不混入后续shared_collision构建的结果。

4. 更新触发和预算还缺少与局部执行的配合。
   协同分支检查旧参考约每0.25秒一次，失败后等0.75秒再试；仍可能用0.60秒预算
   优化剩余较长参考，本批静态刷新样本的初始化轨迹时长约12.85～13.10秒。
   搜索/验收失败、等待下一轮和ESDF等待会把新参考交付延迟放大到秒级。
   动态短轨迹也会超时，所以预算只是问题的一部分。

七、建议的改进顺序（本次尚未实施算法/实车修复）

1. 先修原控制链的冻结恢复死锁，给差速底盘一个经过碰撞检查的位姿恢复过程。
   保留安全约束，不能仅扩大恢复阈值或强制最小速度；否则基线对照会混入控制缺陷。
2. 增加可行性恢复/时间分配环节，确保优化收敛后能满足轮速和轮加速度边界。
   统一两层动态约束含义；增加预算不能代替这一步，放宽最终检查也不能解决物理约束。
3. 把经过检查的局部绕行、可接续状态和时间反馈给慢层，作为初始化/接续依据。
   新参考交付时按最新执行状态复核，处理已过期前缀与速度连续性。
4. 对动态碰撞代价做函数级剖析，再决定缓存、查询加速或并行化；根据任务规模配置预算。
   本批没有依据支持优先通过CPU绑核、增加线程或提高速度来解决主要问题。
