一、起步和行进时的反复归零：地图时效检查是本次主要直接触发因素

区间                       目标1全程       目标2起步前20秒
MPPI 周期数                527             179
交付成功                   276             51
未交付                     251（47.63%）   128（71.51%）
明确 map_age_ok=false      173             110
慢层撤销轨迹               3               0
无可行候选拒绝             0               0

“交付成功”包括合法的零速保持，不能等同实际运动。“未交付”也不等同独立停车次数。
目标1记录到119次非零速度指令转为零指令；这是控制消息切换次数，不是实车完全停稳119次。
源码 whole_body_mppi.py 的 reject() 首先无条件调用 stop_base() 发布零速。LOCAL_RETRY 只避免升级为 tracking_fault，并不保持非零控制。因此失败、恢复、再失败会直接形成速度脉冲。

目标2起步前20秒：输入捕获时地图年龄中位数351.47ms，已超过350ms门限。实际执行规划的周期耗时中位数27.08ms，95分位60.42ms；没有 planning_deadline 或 delivery_deadline 拒绝。该阶段不能归因为“MPPI求解太慢”或“慢层一直换轨”。
目标1另有10次规划阶段截止、20次交付阶段截止拒绝；规划耗时中位数37.35ms，交付累计耗时95分位99.74ms，超过同一周期95ms门限。因此交付计算也是独立问题，但不能拿它解释目标2全部起步卡顿。

地图链实际开销：
- 目标1/2每次ESDF计算格数中位数约213万/202万。
- ESDF计算耗时中位数104/111ms，95分位144/171ms。
- 从融合完成到首次有效导出，中位数165/170ms，95分位219/237ms；随后还有订阅、控制周期等待及交付复核。
- 目标2记录的1156次计算全部执行负距离完整变换，该部分占compute累计耗时约36.2%。以前做过局部/行级优化，当前实际计算域仍很大。
地图350ms门限按融合时间计龄。点云源时间到导出的310ms左右中位数使用另一时间起点，不能直接拿它与350ms门限作同口径比较。

二、第一段三次慢层碰撞撤轨：高度指向车体自身回波漏滤

三次撤轨发生在10:38:56.989、10:39:01.986、10:39:11.089，均有 raw_latest 实时占据碰撞见证。
对两路已录点云按源时间TF还原，找到同体素实际保留点。它们仅在当前自滤球加1cm余量之外0.122、0.621、0.552毫米。
后两次相隔9.10秒，世界坐标移动0.321米，传感器坐标只变化2.54毫米，强烈支持随车自返回或附着物；高度也不符合当前地面过滤范围。
第二次实际点距查询球心0.1591米，尚在0.1553米碰撞阈值外，但5cm体素中心距球心0.1514米，触发碰撞。体素量化直接参与该次撤轨。
当前PCD同体素无点，最近静态点超过0.61米；raw_latest函数本身也排除静态占据邻域。证据指向实时近车体占据，不能归因于预建地图整体阻挡。
边界：没有自滤前原始点云和现场图像，尚不能确定具体反射部件；当前PCD字节未与历史归档逐一核验。不能仅凭点靠近车体就删除真实近距障碍。

三、第二段数秒停顿：CAN连续，主机反馈链出现空档，继而阻断点云

原始CAN关节反馈三个ID（0x2a5/0x2a6/0x2a7）到达间隔中位数均约5ms，全记录最大间隔约10.74ms。
但 /joint_states_single 最长接收空档为2.233秒，源时间间隔最大2.236秒；执行状态话题也在相同区间缺帧。
五次LiDAR超时撤轨附近，ROS关节流空档约1.05、1.42、2.23、1.58、1.27秒；这些窗口CAN最大到达间隔不超过9.01ms。
日志与源码连接的链路为：
  主机反馈接收/校验/发布链停顿
  → 自滤节点认为关节反馈过期，抑制点云
  → 地图实时输入超过750ms
  → LiDAR超时、撤销轨迹、停车和恢复规划。
前三次超时前，新地图计算只需85/94/115ms，融合到首次导出147/142/166ms，但缓存有效标记已为0，关节年龄269/279/299ms。它们不能解释成“这次地图算了超过350ms”。
定位边界：已排除这些长空档由CAN物理报文中断直接造成；未录SDK/驱动线程栈，不能声称已确定是哪把锁、GIL或哪个函数阻塞。
先前300ms宽限只改变驱动持续故障处置，MPPI仍有150ms有效性检查；秒级空档也远超300ms，因此加宽到300ms不会解决本轮问题。

四、动态障碍没有进入预测几何，不能把本轮称为成功运行了预测避障

全程4822帧 /dynamic_points 全空，运动资格计数4836帧全部为0；第二目标2268帧动态点云也全空。
跟踪器持续有候选簇和已关联轨迹，健康检查通常通过，参数没有关闭动态预测。
第二目标有3条候选观测通过速度、位移、持续时间等其他进入条件，仅被 surface_translation 表面平移一致性检查拒绝，约在10:42:11、10:43:08、10:43:09。
该检查要求历史首尾表面双向最近邻匹配：按净位移平移后进入5cm容差，并较不平移时显著改善。日志没有记录双向距离明细和首尾表面，尚不能区分具体不等式失败，也不能据此直接认定容差过严或这些簇就是用户。
明确结论：你已经进入并离开路径，但本轮没有合格运动目标进入后续外推与扫掠几何。实时占据仍在保护机器人，并确实触发停车；“预测范围清空”日志在这里常表示输入集合为空，不能证明预测并避开了运动目标。
MPPI仍可能依据占据做反应式避障，不能说MPPI完全没运行；但本轮不能用于证明动态预测输入及自主绕行已经贯通。

五、为什么此前反复修改仍卡顿

历史改动处理了不同局部问题：
- snapshot-resync：完整/增量地图缓存失配和重同步。本轮导航中没有该decode失败；地图时龄拒绝仍大量存在。
- perception/obstacle/map-stop recovery：保留目标并允许恢复，未消除恢复前的停车。
- feedback-grace300：降低短暂反馈故障升级为锁停的概率，未消除150ms执行门控和秒级软件空档。
- 参考相位、速度能力、换档及调头改动：改善快慢层轨迹衔接，不能消除输入无效和近车体实时占据。
- 地图计算优化：离线小区域或单阶段改善，没有证明当前约200万格加提交、发布、等待的整条链满足稳定控制需求。

此前验证闭环不够：局部错误不再出现，不等于同一场景下控制输出连续。把局部离线通过或一段流畅，扩大为“整体卡顿已解决”，结论过早。版本记录本身也仍标注实车待验证。
本轮已把四条链分别落实到周期统计、碰撞点、CAN对ROS时序、动态资格门控；后续不能再只按警告名称统一放宽超时，也不能每发现新问题就丢掉先前未验收的问题。

六、最小修复与验收顺序（尚未实施）

1. 地图到控制交付链：用本轮真实约200万格数据回放，分别核对变化范围扩张、负距离完整变换、导出和控制等待，降低数据交付年龄和重复工作。以有效命令交付率及零速切换为验收指标，不能只汇报一个ESDF函数快了多少。
2. 保持独立检查关节发布链与近车体漏滤：定位SDK/驱动发布关键路径的秒级停顿；用已保存点云验证最小自滤模型修正，同时检查真正近车体障碍仍被保留。不能简单扩大整片盲区。
3. 对动态表面门控做定向离线复现，保留静态背景负样本，验证运动目标能够通过而静态表面不被当成运动物体。仅修改已定位的判据，不添加新的跟踪管理框架。
4. 上述离线验证通过后，实车以同一版本一次覆盖空旷前进、调头、倒退、障碍进入和离开。分别核对动态候选识别、MPPI非零避让交付、慢层衔接与到达；未完成这条链不能标记“双时间尺度动态避障验证通过”。

七、资源与记录边界

运行期间最低MemAvailable约1702MiB（1.66GiB），没有证据将本轮主要卡顿归为内存耗尽。交换区使用有增加，但没有完整逐秒换页速率，不能声称全程没有换页影响。
四个主要记录器合计约占0.4个CPU核；记录和临时开启的地图DEBUG日志并非零开销。缺少有/无记录同负载对照，无法量化它对本轮尾延迟的贡献。
地图事件记录有32次、128MiB上限，晚期不能保证每次事件都有完整同代地图；core和geometry数据用于连续时序和窄窗几何分析。
控制指令按bag接收时间作图，MPPI按诊断源时间划分周期；不把命令切换等同实测轮速停稳，也不把最近日志配对当成每次精确因果匹配。
/mm_controller_node/car_cmd 使用Twist承载位置和速度混合数据：linear.x是目标位置x，不是线速度。汇总图只绘制标准 /cmd_vel，避免将其误作原生速度比较。
